## 一、Standards 轴（是否符合仓库文档化编码标准）

已核实：`go build ./...`、`go vet ./...`、`go test ./...` 全绿；
golden 测试（`pkg/gen/gen_test.go:257` `TestGoldenExampleDTO`）强制提交版
`zz_generated.validation.go` 与重新生成结果一致，且生成结果满足全部文档化语义——
同一字段只报第一个失败规则、pointer `omitempty` 仅在 nil 时短路、string 长度按 UTF-8 字符数、
`Validate()` 不修改接收对象且不调用 `FillDefaults()`、依赖仅限 `errors`/`errorx`/`check`、临时文件 + rename 原子写入。

### 1.1 文档化标准违规（硬性，低严重度）

- **`example/grpc/grpc.go:23-24`**（违反 AGENTS.md「注释：导出 API…简洁中文注释」；README「错误模型」）
  —— `ValidateRequest` 的注释声称「结构化信息通过 err.CollectFieldErrors 获取」，但第 27 行实际返回
  `status.Error(..., err.Error())`，结构化信息在转换时被抹掉；对返回的 error 调用 `errorx.CollectFieldErrors`
  只会得到 nil。且 `err.CollectFieldErrors` 读起来像一个不存在的方法。
  应改为：结构化错误需在转换前通过 `req.Validate()` 获取（`grpc_test.go` 自身的注释已经这么写）。
- **治理告警**：`AGENTS.md`（权威标准）未被 git 跟踪，未纳入本次评审的 commit 集合，建议尽快提交。

### 1.2 smell baseline 发现（判断项，仓库生成器风格大多认可这些写法）

- **重复代码（Duplicated Code）** —— `pkg/parser/parser.go:363-390`（`numericLiteral`）与 `394-430`（`ParseDefault`）
  存在完全相同的 ParseInt/ParseUint/ParseFloat + `Format…` + `bits==0→64` 兜底代码块；可提取共享的规范化 helper。
- **数据泥团（Data Clumps）** —— `(kind, bitSize, isPointer)` 贯穿所有 parser 函数签名
  （`ResolveKind` 156、`ParseRules` 269、`fillRule` 315、`numericLiteral` 363、`ParseDefault` 394）；
  `pkg/runtime/runtime.go:125` 的 `splitIndex` 返回 5 元组 `(name, idx, hasIdx, key, hasKey)`。建议打包成小类型。
- **重复 switch（Repeated Switches）** —— `pkg/gen/gen.go:208-241` 的 `failExpr` 有符号/无符号分支仅差
  `int64`/`uint64` 强转；`pkg/check/check.go:36-66` 的 `OneOfString/Int/Uint` 循环形状相同。
  可用按类型参数化的 helper 消除重复（对生成器而言可接受，仅提示）。
- **费解命名（Mysterious Name）** —— `pkg/gen/gen.go:75` `importsUsed(...) (useerr, useCheck bool)`：
  `useerr` 容易读成 "user"；`useErr`/`useErrors` 更能表达意图。
- **中间人（Middle Man，轻微）** —— `pkg/parser/parser.go:150` `FieldName` 与 `runtime.go:143` `jsonFieldName`
  是 `errorx.FieldName` 的薄包装（它们额外做了 tag 类型转换，属于边界情况）。

生成文件本身：`pkg/gen` 产出的内容没有问题。

### 1.3 评分：**8/10**

所有文档化语义与生成标准均被严格满足并有 golden 测试兜底；唯一的硬性违规是一处示例文档注释误导，
其余 smell 均为轻微判断项，且仓库明确的生成器风格大多认可这些写法。

## 二、Spec 轴（是否忠实实现 issue / PRD / 规格）

### 2.1 缺失或部分实现的需求

- 规格 Test Plan §4 要求 golden 测试覆盖「非法规则不写文件」（`docs/spec/validation-gen.md:369`）。
  该行为已存在（`cmd/valgen` 在解析失败时不会走到 `WriteFile`），PR 001 也声明做了手工验证，
  但没有「非法规则不触碰已有文件」的自动化测试，仅有 `TestWriteFileAtomic` 覆盖原子性。→ 部分实现。
- 规格 Test Plan §6 要求 HTTP 集成测试覆盖「提供零值」（`docs/spec/validation-gen.md:408`）。
  `example/http` 测试覆盖了缺字段、header/uri/query 失败与默认值，但从未覆盖「显式提供零值」的场景；
  该场景只存在于 `example/dto` 的一致性测试中。→ 部分实现。
- 规格 PR 验收要求「PR 包含 spec、issue、test、goal 和验收结果」（`docs/spec/validation-gen.md:491`）。
  PR 002 记录了 issue/pr，但没有 `docs/goal/002-*`（只有 `001-静态校验生成器.md`），002 的 gitOps 记录不完整。

### 2.2 范围外实现（规格未要求）

- `gen.Generate` 为每个类型都生成空的 `FillDefaults()`，即使该类型没有任何 `default` tag
  （见 `example/dto/zz_generated.validation.go` 中 UserProfile/Order/NoValidate）。规格只在类型使用 default 时定义
  `FillDefaults`，这增加了噪音。
- `pkg/parser/parser.go` 的 runtime-only 拒绝清单超出规格枚举范围
  （额外加入了 eqcsfield/necsfield/gtcsfield…、eq、ne、excluded_* 等）。属无害加固，但超出规格。
- `example/http` 新增 `SettingsHandler` 默认值演示，超出 issue 002 要求的场景。相关但属于额外内容。

### 2.3 已实现但实现有误 / 文档与实现不一致

- **`example/dto/dto.go:61` 声称 NoValidate「不生成 FillDefaults」，但提交的生成文件中存在
  `func (x *NoValidate) FillDefaults() {}`**。由于重新生成结果与提交版逐字节一致（golden 测试通过），
  dto.go 的注释是错的，违反 issue 002 需求 3「所有示例与 README 内容必须与代码行为一致」
  （`docs/issue/002-HTTP绑定示例与README.md`）。
- 其余未发现错误：已逐一对照 validator/v10.30.1 源码核实——
  nil 指针语义（`Handle` nil → min、`Nick` nil → required）、float32 参数使用 `asFloat32`、
  email 正则与 `emailRegexString` 逐字节一致、同字段首个失败即短路与 validator 的 `return`-on-failure 一致。
  `go build/vet/test/test -race` 全绿；生成文件无反射、仅 import `errors` + `errorx`/`check`；
  golden 测试确认重新生成 == 提交文件；README 代码片段与 `example/http/main.go`、`dto.go` 一致。

### 2.4 评分：**8/10**

规格几乎全部实现，且语义已对照 validator/v10 逐一验证；扣分点：
缺少「非法规则不写文件」自动化测试、「显式零值」HTTP 用例未覆盖，以及 `FillDefaults` 相关注释与代码矛盾。
